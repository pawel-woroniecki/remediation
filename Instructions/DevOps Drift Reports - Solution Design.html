📋Executive Summary

The DevOps Drift Reports system automatically detects discrepancies between what is defined in source code (GitLab) and what is actually deployed in GCP environments. It runs six scheduled Cloud Run Jobs every morning and populates BigQuery tables that power Looker Studio dashboards for both operations teams and management.

ℹ️
Why it exists

Manual comparison between code and deployed infrastructure does not scale across 40+ repositories. This system provides automated daily visibility into four types of drift: schema differences, missing branch merges, file content divergence, and abandoned BigQuery datasets.

Commit DriftCommits present in one branch but missing from anothermaster ↔ production ↔ testDEV

Components

Orchestration
Cloud Scheduler

Triggers each Cloud Run Job via HTTP POST to the Cloud Run Admin API. 6 schedules staggered from 05:00–05:50 Berlin time.

Compute
Cloud Run Jobs

Stateless containers (Docker image) running the Python report scripts. Each job scans all repos in the fastoss subgroup in parallel.

Source of truth
GitLab

All repositories in the fastoss subgroup. Repos are cloned at job start. demo_* repos are excluded automatically.

Storage
BigQuery — devops_reports

Central dataset in tefde-gcp-fastoss-dev holding all findings, execution metadata, and pre-built dashboard views.

Storage
GCS

Markdown/CSV report files uploaded per execution. Links are surfaced in the env_drift_summary dashboard for drill-down.

Visualisation
Looker Studio

Eight dashboards built on top of BigQuery views: Management (health grid), per-environment env drift (prod / test / dev), commit drift with staleness table, file drift, job run status, and orphan datasets.

IaC
Terraform

All Cloud Run Jobs, Cloud Scheduler, BigQuery tables and views are defined in Terraform. Apply is required after any infrastructure change.

Secrets
Secret Manager

GitLab Personal Access Token stored as gitlab-token in tefde-gcp-fastoss-dev-gke. Read by jobs at runtime.

⚙️How each report works

Environment Drift (env_drift)

prod · test · dev

Compares what is defined in the git branch (SQL DDL files and dbt YAML models) against the actual BigQuery schema in the target GCP project. Detects objects that exist in code but are not deployed, objects that are deployed but have no code definition, and objects where the schema or definition has diverged.

env_drift flow — per environment
flowchart TD A["Cloud Scheduler trigger"] --> B["Cloud Run Job starts\nloads GitLab token from Secret Manager"] B --> C["Clone all repos in fastoss subgroup\nskip demo_* repos"] C --> D{{"For each repo\n(parallel)"}} D --> E["Parse DDL / dbt YAML\nfrom git branch\nproduction / test / master"] D --> F["Query BQ INFORMATION_SCHEMA\nin target GCP project"] E & F --> G["Compare schemas\nobject by object"] G --> H{{"Differences\nfound?"}} H -- "Yes" --> I["Write rows to\nenv_drift_findings\n(one row per drifted object)"] H -- "No" --> J["Write execution record\nto executions table\nstatus = success"] I --> J J --> K["Upload report.md\nto GCS bucket"]

Commit Drift (commit_drift)

Branch comparison

Finds commits that exist in one branch but are absent from another. This reveals cherry-picks that were never back-merged, hotfixes applied directly to production, or test-environment changes never promoted to master. The companion Commit Staleness table (powered by the branch_drift_staleness BigQuery view) shows how many days the oldest unmerged commit has been waiting in each direction, surfacing drift that has been accumulating for weeks or months.

commit_drift flow
flowchart TD A["Cloud Scheduler trigger"] --> B["Clone all repos"] B --> C{{"For each repo\n(parallel)"}} C --> D["Compare 6 branch pairs:\nmaster<>production\nmaster<>test\nproduction<>test\n(both directions each)"] D --> E["Find commits in right branch\nnot present in left branch\n(git log A..B)"] E --> F["Write KPI summary\nto branch_drift_kpis\n(one row per repo x direction)"] F --> G["Write commit detail\nto branch_drift_evidence\n(one row per commit x file)"] G --> H["Write execution record\nto executions table"]

Branch directions explained

DirectionMeaningMust be 0?
production not in masterHotfix in production never merged back to master🚨 Yes
production not in testProduction commit never promoted to test🚨 Yes
test not in masterTest-env commit never merged to master🚨 Yes
master not in productionFeature merged to master, not yet released✓ OK
master not in testFeature merged to master, not yet in test✓ OK
test not in productionFeature tested but not yet released✓ OK

File Content Drift (file_drift)

Branch comparison

Complements commit drift by detecting file-level differences between branches regardless of commit history. Catches cases where files were modified directly (e.g. by force-push or rebase) without creating a traceable commit difference.

file_drift flow
flowchart TD A["Cloud Scheduler trigger"] --> B["Clone all repos"] B --> C{{"For each repo\n(parallel)"}} C --> D["git diff --name-status\nbetween branch pairs"] D --> E["Classify each file:\nAdded / Modified / Deleted / Renamed"] E --> F["Write KPI summary\nto branch_drift_kpis\n(drift_type = content)"] F --> G["Write file detail\nto branch_drift_evidence"] G --> H["Write execution record"]

Orphan Datasets (orphan_datasets)

Prod only

Lists BigQuery datasets in the production GCP project that have no corresponding source code reference in any repository. These are candidates for cleanup or adoption — they represent storage cost and governance risk.

orphan_datasets flow
flowchart TD A["Cloud Scheduler trigger"] --> B["Cloud Run Job starts"] B --> C["List all BQ datasets\nin tefde-gcp-fastoss-prod\nvia INFORMATION_SCHEMA"] B --> D["Clone all repos\nfrom GitLab"] D --> E["Extract dataset references\nfrom DDL / dbt / CI files"] C & E --> F["Find datasets with\nno code reference"] F --> G["Score each orphan\nby risk: age x size x table_count"] G --> H["Write to orphan_datasets\nand orphan_dataset_objects"] H --> I["Write execution record"]

📐Metrics reference

Environment Drift metrics

FieldDescriptionHow to interpret
bq_findingsCount of BigQuery objects with schema drift0 = all good. Any value > 0 means deployed schema differs from code.
gcs_findingsCount of GCS objects with drift0 = all good. Non-zero means files in Composer bucket differ from repo.
drift_categoryType of discrepancy foundonly_in_env: deployed but no code; only_in_source: in code but not deployed; schema_mismatch: column types differ; definition_mismatch: view SQL differs.
severityImpact rating of the drifthigh: breaking change (type mismatch, missing object); medium: significant difference; low: cosmetic / whitespace.
in_env_not_in_codeObjects deployed that have no git definitionShadow objects — created manually or by a process not tracked in git. Should be codified or removed.
in_code_not_in_envObjects defined in git but not yet deployedPending deployments. Normal during a release but concerning if persistent for days.
content_mismatchObjects that exist in both but differSchema has drifted post-deploy. Most critical — production is running code different from the repo.

Commit Drift metrics

FieldDescriptionHow to interpret
unique_commitsNumber of commits present in one branch but not the otherFor red-flag directions (production not in master etc.): must be 0. For acceptable directions: informational.
drift_directionWhich branch has the extra commitsFormat: "X not in Y" — X has commits that Y lacks. See table in the commit_drift section above.
severityRisk level of the drifthigh: production-critical direction; medium: test branch divergence; low: minor.
red_flagsSum of unique_commits for the 3 critical directions onlyShown in the management dashboard. Must be 0. Non-zero = immediate action required.
distinct_authorsNumber of distinct commit authors contributing to the driftHelps identify who needs to create the merge request.

File Drift metrics

FieldDescriptionHow to interpret
unique_filesTotal files differing between the two branchesHigher = more diverged. Focus on files_deleted first — deletions in production not in master are most dangerous.
files_addedFiles present in right branch, missing in leftNew files not yet promoted. Normal ahead of a release.
files_modifiedFiles that exist in both branches but with different contentMost common. Compare with commit drift to understand whether this is tracked or an out-of-band change.
files_deletedFiles deleted in right branch but still in leftHigh priority — production may be missing a file that master still has (or vice versa).

Orphan Dataset metrics

FieldDescriptionHow to interpret
orphan_statusClassification of the datasetorphan: confirmed no code reference; possible_orphan: weak match found; matched: code reference found (should not appear in findings).
risk_score0–100 score combining age, size, and table countScore > 75: high risk, prioritise for cleanup or adoption. Score < 25: likely safe to ignore short-term.
total_storage_mbTotal storage used by all objects in the datasetLarge orphans with high risk score are the primary cleanup candidates.
days_since_modifiedDays since the most recent object in the dataset was changed> 180 days with no code reference = strong orphan signal.
dataset_count (trend)Number of orphan datasets on a given dayIncreasing trend = orphan growth is outpacing cleanup. Flat or decreasing = healthy.

🚨When to act

⚠️
Daily check

The recommended workflow is to open the Management Dashboard each morning after 06:00 Berlin time (all six jobs will have completed by then). Any red cell is a starting point for investigation.

DEV team actions

SignalWhere to see itSeverityAction required
Red flags > 0
production or test commits missing from master		 Management Dashboard → Red flags column
Branch Drift page → ⚠ columns		 🚨 Immediate Open a merge request to back-merge the missing commits into master. Investigate why a commit landed in production without going through master (hotfix process failure?).
content_mismatch (high severity)
deployed schema differs from code		 Env Drift Summary → BQ/GCS findings > 0
Env Drift detail page → severity = high		 🚨 Immediate Determine whether the deployment or the code is the source of truth. Either re-deploy or update the DDL in git. Raise with the release manager if in prod.
in_code_not_in_env > 0
objects defined but not yet deployed		 Env Drift detail page → in_code_not_in_env column ⚠️ Monitor Normal during a release window. If persistent for > 2 days after a release, trigger a re-deploy or investigate pipeline failures.
schema_mismatch (medium severity) Env Drift detail page → drift_category = schema_mismatch ⚠️ Investigate Review the column type difference. If intentional (migration), update the DDL in git. If unintentional, roll back or re-apply the correct migration.
master not in production > 0 Branch Drift page → master not in production column ✓ Normal No action needed. This means features are merged to master awaiting the next release to production. Expected before a release cut.
in_env_not_in_code (low severity) Env Drift detail page → in_env_not_in_code ✓ Low priority Object exists in GCP but has no git definition. Either codify it (add DDL to the repo) or plan for removal if it is no longer needed.

OPS team actions

SignalWhere to see itSeverityAction required
Job status = failed Job Status page → Status column 🚨 Immediate Check Cloud Run logs in GCP Console for the failed job. Common causes: GitLab token expired, IAM grant missing, network issue. The job retries once automatically; if still failing, investigate manually.
Orphan dataset risk_score > 75 Orphan Datasets page → risk_score column 🚨 Action needed Contact the dataset owner (see owner field). Either add a code definition to the owning repo, or schedule the dataset for deletion if it is confirmed unused.
Orphan count trend increasing Orphan Datasets → Over time chart ⚠️ Monitor Investigate which datasets were added to the orphan list recently (filter by date range). Escalate to the data platform team if growth exceeds 10% week-over-week.
env_drift job running but all repos skipped executions table — check status = skipped rows ⚠️ Investigate Repos are skipped when the GitLab clone fails or the repo has no recognisable DDL/dbt structure. Check if a new repo type was added that the scanner doesn’t recognise.
All jobs = success, management dashboard all green Management Dashboard, Job Status page ✓ All clear No action needed. The system is healthy.

💡
Rebuilding the Docker image

After any Python script change, rebuild the Docker image and push it to Artifact Registry (europe-west3-docker.pkg.dev/tefde-gcp-fastoss-dev-gke/devops-reports/devops-reports-runner). Then run terraform apply to update the Cloud Run Jobs — Cloud Run resolves image tags to a specific digest at deploy time, so a new push alone does not take effect until the job definition is updated. See Instructions/Building and Releasing a New Image Version.md for the full two-step release process.

⚙️
Infrastructure changes require terraform apply

Changes to Cloud Run Job environment variables, schedules, BigQuery view definitions, or table schemas only take effect after terraform apply is run from the TEF remediation/Terraform/ directory. Editing the .tf files alone is not sufficient.
