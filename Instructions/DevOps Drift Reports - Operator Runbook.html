📋Overview

The DevOps Drift Reports system runs seven Cloud Run Jobs every morning between 05:00 and 06:00 Berlin time. By 06:20 all jobs will have completed, and the Looker Studio dashboards will reflect the latest results. This runbook tells you what to look at each morning, what a normal state looks like, and what to do when something is wrong.

ℹ️
Five report types, nine dashboards

The system monitors five types of drift: BigQuery schema differences (Env Drift), missing commits between branches (Commit Drift), file content differences between branches (File Drift), BigQuery datasets with no code ownership (Orphan Datasets), and BigQuery table structure inconsistencies across environments (BQ Structure Drift). The nine dashboards surface these at different levels of detail.

⚠️
Important: always verify the data is fresh

Before acting on any finding, confirm the dashboard is showing today's run. Check the execution_ts or Run date filter in the dashboard. If the latest row is from a previous day, one or more jobs may not have run — go to Job Run Status first.

✅Daily check sequence

Perform this sequence each morning after 06:20 Berlin time. The whole check takes 5–10 minutes when everything is healthy.

1
Open Job Run Status dashboard

Verify all seven jobs show status = success and ran today. Check that repos_processed > 0 for commit drift and file drift. A job that succeeded but processed zero repos is a silent failure — treat it as a failed job.

2
Open the Management Dashboard

Scan the red/green health grid. Any red cell in the Red flags column (commit drift) requires immediate action. Other red cells should be noted and investigated using the detailed dashboards.

3
If red flags > 0 → open Commit Drift dashboard

Find the affected repository. Confirm the drift direction (see the directions table in the solution design). Notify the relevant DEV team to open a merge request. Log the incident.

4
Check Env Drift Summary — Prod for high-severity findings

Filter for severity = high. Any high-severity env drift finding in production means a deployed schema differs critically from the code definition. Escalate to the DEV lead for the affected product.

5
Review Orphan Datasets for new high-risk entries

Check for any dataset with risk_score > 75 that was not in yesterday's report. Contact the dataset owner to confirm whether it is safe to delete or needs a code definition added.

6
All clear — record in the daily log

If no red flags, no high-severity env drift, and all jobs ran successfully, record a brief status update in the OPS daily log and close the check.

📊Dashboard guidance

Management Dashboard — Discrepancy status in repositories

Daily start point

This is the first dashboard to open each morning. It shows a red/green health grid — one row per repository, one column per report type. It is designed to answer "is anything broken today?" with a single glance.

What to look at

ElementMeaningAction
Red flags columnCommits in production or test that are missing from master. Must always be 0.🚨 Immediate — open Commit Drift dashboard for the affected repo.
Red cells in Env Drift columnsHigh-severity BigQuery schema drift found in that environment for that repo.Open Env Drift Summary for the relevant environment and locate the specific findings.
All greenNo new critical drift across any dimension today.No action needed. Record in daily log.
Stale "Last run" dateA report type did not run today — the grid is showing yesterday's (or older) data.Check Job Run Status for a failed or missing job execution.
⚠️
Green does not mean "no drift" — it means "no critical drift"

The management dashboard aggregates at a high level. Medium and low severity findings are rolled up into amber or hidden. Always follow up with the detailed dashboards if you see amber cells or if the dev team reports a concern.

Job Run Status

Infrastructure health check

Shows per-run statistics for env drift, commit drift, file drift, and orphan datasets, sourced from the four job-summary BigQuery views. This is the most important dashboard for detecting infrastructure problems — a job that "succeeded" but did no work is just as problematic as a failed one.

SELECT repo, left_branch, right_branch, run_date

Environment Drift Summary — Production

Highest priority

Shows per-repository schema drift against the production GCP project. Production drift findings require prompt attention because they indicate that what is running in prod does not match what is defined in source code.

What to look at

SignalSeverityMeaningAction
content_mismatch, severity = high🚨 CriticalA deployed table or view differs critically from its code definition — schema types mismatch or a column is missing.Notify the DEV lead for the affected product immediately. Include the object name, dataset, and the finding detail. A production schema mismatch can cause job failures.
only_in_env (object has no code)🚨 InvestigateAn object exists in production BigQuery but has no corresponding DDL in git. It was created manually or by an undocumented process.Identify the owner and ask them to either add DDL to the repo or submit a removal request. Do not delete without owner confirmation.
only_in_source (object not yet deployed)⚠️ MonitorDDL exists in git but the object is not deployed in production. Normal within 24 hours of a release.If persistent for > 2 days after a release, ask the DEV team whether the deployment succeeded.
definition_mismatch, severity = medium⚠️ Notify DEVA view's SQL differs between git and deployed. Often a whitespace or formatting difference, but may indicate an out-of-band modification.Share the finding detail with the DEV team. They will confirm whether the deployed version or the git version is canonical.
No findings for all repos✓ OKAll objects in production match their code definitions.None.
📄
Linking to the detailed report

Each row in the env drift summary has a Report link column containing a direct link to the report.md file for that run, stored in GCS. Click the link to see the full human-readable breakdown of all findings for that repo and execution.

Environment Drift Summary — Test & Dev

Lower priority than prod

Same structure as the Prod dashboard, but targeting the test and dev environments. Findings here are lower priority — they indicate pre-production misalignment but do not directly affect production users.

Key differences from prod

SignalAction
High severity finding in testNotify the DEV team — this will block promotion to production if not resolved. Not an emergency but should be addressed before the next release cut.
High severity finding in devInformational for the DEV team. Low urgency. Track and include in the next sprint review if persistent.
All repos have only_in_source findingsNormal when a feature branch has been merged but the test environment has not been re-deployed. If it persists for more than 1 week, prompt the DEV team about the deployment state.
All findings suddenly zero (when they previously had some)Verify that the job ran successfully and cloned repos correctly — an empty finding set after a long period of findings may indicate a scan failure, not a cleanup.

Commit Drift

Red flags = zero-tolerance

Shows commits present in one branch but absent from another. The dashboard includes a Commit Staleness table showing how many days the oldest unmerged commit has been waiting — this makes slow-accumulating drift visible before it becomes critical.

Direction reference — which are the critical ones

DirectionCritical?Meaning
production not in master🚨 Must be 0A commit was applied to production without going through master. Hotfix process failure.
production not in test🚨 Must be 0Production has code that was never tested.
test not in master🚨 Must be 0Test environment has commits never merged to master — risk of losing work.
master not in production✓ ExpectedFeatures merged but not yet released. Normal before a release cut.
master not in test✓ ExpectedFeatures on master not yet promoted to test. Normal.
test not in production✓ ExpectedFeatures tested, awaiting production release. Normal.

Staleness table — when to escalate

StalenessAction
oldest_unmerged_days < 7 daysMonitor. Likely pending the next release cycle.
oldest_unmerged_days 7–30 daysNotify the repo owner. Confirm whether the drift is intentional (e.g. a long-running feature branch).
oldest_unmerged_days > 30 daysEscalate to the DEV lead. Drift this old usually indicates a forgotten merge request or a process failure.
📅
Use the Run date dropdown

The dashboard includes a Run date filter. When investigating historical drift, always select the specific date you want rather than relying on the default — the default shows the most recent run, which may have resolved drift that was present earlier and that you are trying to verify.

File Content Drift

Complements commit drift

Detects file-level differences between branches regardless of commit history. This catches out-of-band modifications (force-pushes, direct edits) that would not show up in commit drift.

What to look at

SignalSeverityAction
files_deleted in production > 0 (not in master)🚨 InvestigateA file was deleted in production that still exists in master. This is a strong signal of an untracked change. Notify the DEV lead — the file may need to be restored or the deletion needs to be committed to master.
Large files_modified count with low commit drift⚠️ InvestigateFiles differ but there are few or no commits explaining the difference. Could indicate a force-push or rebase that rewrote history. Correlate with commit drift for the same repo and direction.
High unique_files count increasing day-over-day⚠️ MonitorFile divergence is growing, suggesting an active branch that is not being merged back. Alert the repo owner.
Low unique_files count, all in master not in production✓ NormalPending release. No action needed.
Findings persist day-after-day even though files exist in both branches⚠️ Acknowledged driftThe report uses merge-base comparison — findings show what production changed since the last shared commit, not what is currently different. Files added directly to production keep appearing until the branches are formally re-synced. See the Branch back-merge section for the step-by-step resolution procedure.

Orphan Datasets

Governance & cost

Lists BigQuery datasets in the production project that have no corresponding source code definition. These represent both storage cost and governance risk — they may contain production data with no ownership trail.

What to look at

SignalSeverityAction
risk_score > 75🚨 Action neededIdentify the dataset owner using the owner field or by searching GitLab for the dataset name. Either request them to add a code definition, or confirm the dataset is unused and schedule deletion. Document the outcome in the OPS log.
Orphan count increasing week-over-week⚠️ EscalateNew datasets are being created without code definitions faster than they are being cleaned up. Raise with the data platform team lead — this indicates a process gap in the project onboarding workflow.
New entry with total_storage_mb > 1000⚠️ InvestigateA large dataset appeared without a code owner. This has direct cost implications. Investigate immediately — it may be a misconfigured pipeline writing to the wrong dataset.
Count stable or decreasing, no risk_score > 75✓ OKGovernance is under control. No action needed.
🚫
Never delete a dataset without owner confirmation

The orphan report only confirms absence of a code reference — it cannot confirm the data is unused. Always contact the dataset owner before scheduling deletion. If no owner can be identified within 5 business days, escalate to the data platform team lead.

BQ Structure Drift

Schema governance

Shows BigQuery tables where partitioning or clustering settings differ between prod, test, and dev-gke. A structure difference is not an operational emergency, but it can cause query cost surprises and incorrect partition pruning when code is promoted to a higher environment.

What to look at

SignalSeverityAction
discrepancy = MISSING in prod⚠️ InvestigateA table exists in test or dev-gke but not in production. Check whether it is expected (new table not yet deployed) or an error. Verify the Terraform/DDL definition covers production.
discrepancy = DIFF on tp_type or clustering⚠️ MonitorThe most impactful differences. A table partitioned by DAY in prod but not at all in dev-gke can cause very different query costs. Notify the DEV team owning the dataset to align the DDL across environments.
Count stable or zero✓ OKNo action needed.

🔧Common problems & quick fixes

These are the most frequently occurring issues and their fastest diagnostic paths.

Job failed — Cloud Run error

Symptoms: Job Run Status shows status = failed.

Check in GCP Console:

  • Navigate to tefde-gcp-fastoss-dev-gke → Cloud Run → Jobs
  • Find the failed job → Executions tab → View logs
  • Search for ERROR or Exception

Common causes:

  • GitLab token expired → see GitLab PAT rotation section
  • IAM binding removed → check IAM_admin_instructions.md
  • BigQuery quota exceeded → check BQ quota dashboard
  • Network timeout → job retries once automatically
Job succeeded but repos_processed = 0

Symptoms: Job Run Status shows success but repos_processed = 0 for commit drift or file drift.

Check in Cloud Run logs:

  • Look for "Could not list repositories" or "Empty subgroup"
  • Check whether SUBGROUP_ROOT env variable is set correctly
  • Look for authentication errors fetching the GitLab API

Action: Treat as a failed run. The dashboard data is stale. Fix the root cause and trigger a manual re-run.

Dashboard shows no data for today

Symptoms: Dashboard has no rows for today's date; still showing yesterday's data.

Check:

  • Cloud Scheduler → did the trigger fire at the scheduled time?
  • If trigger fired, check Cloud Run logs for a startup failure
  • If trigger did not fire, check if the schedule is paused

Action: Trigger the job manually from Cloud Run Console → Run now. Then re-check the dashboard after 20 minutes.

Orphan count dropped to 0 unexpectedly

Symptoms: Yesterday showed 25 orphans, today shows 0 and no cleanup was planned.

Check:

  • Cloud Run logs for BQ INFORMATION_SCHEMA errors
  • Check whether the orphan_datasets table was written at all (query directly in BQ)

Action: If the scan failed silently, trigger a manual re-run. If the table was written but shows 0 rows, escalate to the DEV team to investigate the detection logic.

All env_drift findings suddenly zero

Symptoms: A repo that had persistent drift findings suddenly shows 0 findings, but no deployment was made.

Check:

  • Verify the execution_ts — did the job run at all?
  • Check status in the executions table for that repo
  • Look for status = skipped — the branch may be gone

Action: If status = skipped, the production branch no longer exists in that repo. Confirm with the DEV team.

Management dashboard all-green but something feels wrong

Symptoms: Grid is all green, but a DEV team member reports a known issue that should appear.

Check:

  • Is the dashboard date filter set to today?
  • Was repos_processed > 0 for the relevant report type?
  • Is the issue in a medium or low severity finding (these may not turn the cell red)?

Action: Open the detailed dashboard for the relevant report type and filter to the specific repo and date.

🔀Branch back-merge — resolving persistent file drift

The file drift report uses merge-base comparison: it diffs from the common ancestor of two branches to the right-branch tip. This means a file added directly to production (without going through master first) keeps appearing as added even after the same file reaches master through another route — because the merge base (the shared ancestor) has not moved forward.

The finding disappears only when the branches are formally re-synced via a merge commit, which advances the merge base past the point where the files were added.

⚠️
Before merging: confirm the file contents are intentionally the same in both branches.

If the file in production and the file in master differ, a back-merge will produce a conflict or silently pick one version. Review the diff in GitLab first.

Step 1 — Confirm the drift is acknowledged

  1. Open the File Content Drift dashboard and note the repo name, drift direction, and list of affected files.
  2. Check with the DEV team owning the repo: are all listed files intentionally in both branches? If any file should not be in production, stop — do not merge, investigate first.

Step 2 — Review the diff in GitLab before merging

  1. Open the repo in GitLab (e.g. FastOSS_B / ndl_core / inventory_ran).
  2. Go to Repository → Compare (or Merge Requests → New merge request).
  3. Set Source = production, Target = master.
  4. Review the diff. All changes should be the acknowledged files and nothing unexpected.

Step 3 — Create the back-merge MR

  1. Click Create merge request.
  2. Title it clearly, e.g. "Back-merge: sync production → master (acknowledged file drift)".
  3. In the description, list the files being merged and reference the drift report date.
  4. Set Merge method to Merge commit (not squash — a squash merge creates a new commit SHA that will itself appear as drift).
  5. Assign to the repo's DEV lead for approval.

Step 4 — Merge and verify

  1. Once approved, merge the MR. GitLab creates a merge commit on master.
  2. The new merge commit becomes the new merge base between production and master.
  3. Wait for the next scheduled file drift run (daily at 05:30 Europe/Berlin) or trigger a manual run: 
    gcloud run jobs execute devops-reports-file-drift \
  --project=tefde-gcp-fastoss-dev-gke \
  --region=europe-west3
  4. Check the File Content Drift dashboard — the affected files should no longer appear for that repo and direction.
⚠️
Do not use squash merge.

A squash merge creates a brand-new commit SHA on master that does not exist in production. This makes the squash commit immediately appear as master not in production drift in the commit drift report — replacing one drift finding with another. Always use a regular merge commit.

Going forward — prevent direct commits to production

The root cause is files being committed directly to production without going through master → test → production. To prevent recurrence:

  • Ask the GitLab group owner to enable protected branches on production for the affected repo: Settings → Repository → Protected branches → allow merge only from Maintainers, disallow direct push for Developers.
  • Enforce merge requests for all changes to production — no force-pushes, no direct commits.
✅
Resolution checklist

☐ Affected files confirmed as intentional with DEV team  |  ☐ GitLab diff reviewed — no unexpected changes  |  ☐ Back-merge MR created with merge commit (not squash)  |  ☐ MR approved and merged  |  ☐ Next file drift run shows no findings for affected repo/direction  |  ☐ Protected branch rules reviewed to prevent recurrence

🔑GitLab PAT rotation

The GitLab Personal Access Token (PAT) stored as gitlab-token in Secret Manager is fetched at runtime by every Cloud Run Job to clone repos. When it expires, all 7 jobs fail simultaneously with a 401 / authentication error. This section walks through rotating the token end-to-end.

⚠️
Prefer a Group Access Token over a Personal Access Token. A Personal Access Token is tied to an individual GitLab account — if that person leaves, the token is revoked automatically and all jobs stop. A Group Access Token belongs to the ndl_core group and survives staff changes. Ask the GitLab group owner to create a Group Access Token if one is not already in use.

Step 1 — Create a new token in GitLab

  1. Open GitLab and navigate to the ndl_core group.
  2. Go to Settings → Access Tokens.
  3. Click Add new token (or Create group access token).
  4. Set a descriptive name, e.g. devops-reports-runner.
  5. Set an expiry date at least 12 months out. Note it in your team calendar so rotation is planned, not reactive.
  6. Select exactly these two scopes: read_api and read_repository. No other scopes are needed.
  7. Click Create and copy the token value immediately — GitLab shows it only once.

Step 2 — Load the new token into Secret Manager

Run this command from any terminal with gcloud access and the secretmanager.versions.add permission:

gcloud secrets versions add gitlab-token \
  --project=tefde-gcp-fastoss-dev-gke \
  --data-file=- <<< "PASTE_NEW_TOKEN_HERE"

Verify the new version is now the ENABLED latest version:

gcloud secrets versions list gitlab-token \
  --project=tefde-gcp-fastoss-dev-gke

The newest version should show STATE: ENABLED. The Cloud Run Jobs always fetch the latest version automatically — no Terraform or Cloud Run configuration change is needed.

Step 3 — Verify with a test run

Trigger the lightest job to confirm the new token works before the next scheduled run:

gcloud run jobs execute devops-reports-orphan-datasets \
  --project=tefde-gcp-fastoss-dev-gke \
  --region=europe-west3

Wait ~5 minutes, then check Cloud Run → Jobs → devops-reports-orphan-datasets → Executions. Status should be Succeeded. If it still fails with an authentication error, double-check the token was copied correctly (no trailing newline or whitespace).

Step 4 — Disable the old token version (optional but recommended)

Once the test run succeeds, disable the previous secret version to prevent accidental use:

# Replace N with the old version number shown in step 2
gcloud secrets versions disable N \
  --secret=gitlab-token \
  --project=tefde-gcp-fastoss-dev-gke

Step 5 — Notify the team

  • Inform the DevOps platform team that the token was rotated and jobs are healthy again.
  • If the old token in GitLab still exists, revoke it there too (GitLab group → Settings → Access Tokens → Revoke).
  • Add a reminder in your team calendar for the new expiry date, at least 2 weeks before — plan the next rotation before it becomes an incident.
✅
Full rotation checklist

☐ New token created in GitLab with read_api + read_repository scopes  |  ☐ New version added to gitlab-token in Secret Manager  |  ☐ Test run succeeded  |  ☐ Old secret version disabled  |  ☐ Old GitLab token revoked  |  ☐ Team notified  |  ☐ Next-expiry reminder added to calendar

For the full background on why the PAT is stored in Secret Manager and the scope requirements, see Rotating the GitLab PAT.md.

📞Escalation contacts

Use these escalation paths when a finding requires action beyond the OPS team's scope or has been unresolved for more than one business day.

🚨 Production schema drift (high severity)

Escalate to the DEV lead for the affected data product. Include the object name, the drift category, and the GCS report link from the env_drift dashboard.

🚨 Red flag commits (production not in master)

Escalate to the DEV lead and Release manager for the affected repo. This must be resolved before the next production deployment.

⚠️ Infrastructure failure (job not running)

Escalate to the DevOps platform team if the job continues to fail after a manual re-trigger. Include the Cloud Run log excerpt and error message.

⚠️ High-risk orphan dataset (> 75 score)

Contact the dataset owner first. If owner cannot be identified within 2 business days, escalate to the data platform team lead.

⚠️ GitLab token expired

Follow the step-by-step procedure in the GitLab PAT rotation section above. In short: create a new Group Access Token in GitLab (read_api + read_repository), load it into Secret Manager, run a test job, and notify the DevOps platform team.

📋 IAM grant missing

Consult IAM_admin_instructions.md for the required grant. Submit the IAM change request to the TEF IAM Team. They manage the devops-reports-runner service account.

✅
When everything is healthy

A typical all-clear check: Job Run Status shows 7 success rows with repos_processed > 0 for commit/file drift. Management dashboard is all green. No high-risk orphans. BQ Structure Drift shows no new MISSING rows. Record "All drift reports healthy — [date]" in the OPS log and close the daily check.
